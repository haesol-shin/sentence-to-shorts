# SPEC

「결정」은 확정된 제품 규칙이다. 「제안」과 「기술 설계」는 구현 세부이며 확정된 제품 결정이 아니다. 결정의 근거는 [결정 기록](decisions/README.md)에 있다. 목적은 [INTENT](INTENT.md)를 따른다. 용어는 [GLOSSARY](GLOSSARY.md)를 따른다. 실행 계약은 [CONTRACTS](CONTRACTS.md)를 따른다.

## 1. 범위와 실행 형태

- 결정: 앱은 각자 컴퓨터에서 실행한다. 배포판 API profile과 개발 profile은 아래 규칙으로 구분한다.
- 결정: 실행 형태는 두 축으로 나눠 설계에서 함께 고려한다. 사용자 수는 한 명(single user)과 여럿(multi user)이다. 실행 위치는 직접 실행(local)과 서버 호스팅(hosted)이다.
- 결정: 개발 시점과 릴리스 시점을 나눠 본다. 런타임에 필요한 것(TTS 모델, 정렬 모델, 글꼴, 에셋)은 코드가 준비한다. 사용자가 따로 설치하지 않는다.
- 제안: 실행 형태는 설정 하나(deployment profile)로 고른다. 실행 형태마다 달라지는 부분만 인터페이스로 나눈다: 파일 저장, 작업 실행, LLM 연결, 사용자 구분.
- 결정: 배포판의 LLM은 직접 실행과 서버 호스팅 모두 `anthropic_api`가 기본이다. 직접 실행은 첫 실행 때 사용자가 자기 API key를 넣는다. 모델 제공자는 LLM adapter로 바꿔 끼운다.
- 결정: Python과 CPU wheel은 배포물에 동봉한다. 모델은 첫 실행에 manifest와 SHA-256으로 준비한다. 기술 설계: 개발과 배포는 같은 runtime manifest를 쓴다.
- 기술 설계: 여럿 실행에 대비해 소유자 ID(owner_id)를 둔다. 한 명 실행에서는 고정값 하나를 쓴다. 로그인 화면은 이번 MVP에서 구현하지 않는다.
- 결정: 첫 구현은 직접 실행과 한 명이다. 서버 호스팅과 한 명은 같은 코드로 이어 붙인다. 여럿 실행은 데이터 구조만 맞추고 구현은 MVP 이후다.
- 결정: 수정하지 않은 공식 `claude` CLI를 부르는 `claude_cli`는 개발용 선택 adapter다. 배포판 기본값으로 쓰지 않는다.
- 결정: dev profile 기본은 표준 OpenAI-compatible Chat Completions adapter인 `openai_compat`다. any OpenAI-compatible endpoint의 `base_url`과 model 이름을 설정한다. key가 필요하면 keyring 또는 env에서 읽는다. 기여자는 각자 자기 endpoint, 공식 CLI 또는 API key를 쓴다. 한 사람의 endpoint를 공유하지 않는다. endpoint 인증은 설정된 key만 사용한다.
- 결정: 서비스 지원 언어는 한국어와 영어다. 영상 언어는 프로젝트마다 사용자가 고른다.
- 결정: 기술 스택은 Frontend가 React 18, TypeScript 5.7, Vite 6, Tailwind 4이고 Core가 Python 3.11, FastAPI, Pydantic v2, Poetry다.

## 2. 흐름

결정: 다섯 단계다. 단계마다 기본값이 미리 채워져 있다. 사용자는 바꾸고 싶은 곳만 고친다.

결정: 기본값은 사용자 직접 입력, 참고 영상, 프로젝트 프리셋, 주제 기반 LLM 추천 순서로 채운다.

| 단계 | 사용자 입력 | 앱이 채우는 것 | 다음으로 넘기는 것 |
|---|---|---|---|
| 1 스토리 (story) | 영상 언어, 주제, 목표 길이(30초, 1분, 2분), 포맷 카드. 선택: 대본, 재료(MVP는 붙여넣은 글만), 참고 영상, 세부 조정 | 카드가 이야기 틀, 화면 틀, 캐릭터 역할, 말투를 채운다 | 포맷 값, 주제, 재료 |
| 2 시각 (visual) | 그림체, 테마, 캐릭터 (이 순서) | 테마의 배경, 대화창 모양, 색감 기본값. LLM이 캐릭터 부위 조합을 고른다 | 그림체, 테마, 캐릭터 조합 |
| 3a 장면: 대본 확인 | 대본 읽기와 수정, 확인 | LLM이 대본을 쓰고 장면으로 나눈다 | 확인된 대본과 장면 목록 |
| 3b 장면: 미리보기 | 장면 글 수정, 드래그로 순서 변경, 장면 하나 다시 만들기 | 장면마다 정지 미리보기 한 장 | 장면 목록과 순서 |
| 4 소리 (audio) | 목소리, BGM, 자막 방식 변경(선택) | 프로젝트 기본 목소리, 대본 분위기에 맞춘 BGM, 카드의 자막 방식 추천값 | 소리 설정 |
| 5 생성 (generate) | 생성 시작, 결과 확인, 바뀐 장면만 다시 만들기, 프리셋 저장 | 장면별 TTS, 렌더, 조립, mp4. 대본부터 조립까지 이어지는 생성 전체 중 마지막 실행 단계다 | mp4, 프리셋 |

- 결정: 포맷 카드는 1단계에 둔다. 말투와 이야기 틀이 대본 내용을 정하기 때문이다.
- 결정: 시각 단계 순서는 그림체, 테마, 캐릭터다. 캐릭터 에셋이 그림체에 속하기 때문이다.
- 결정: 비싼 일일수록 늦게, 작게 한다. 대본 확인, 장면 정지 미리보기, 전체 생성 한 번, 바뀐 장면만 다시 생성하는 순서다.
- 결정: 대본 확인 전에는 장면 미리보기를 만들지 않는다. 장면 확인 전에는 실제 생성을 시작하지 않는다. 생략할 수 있는 것은 선택 화면 방문이지 확인 동작이 아니다.
- 결정: 목표 길이는 기준이다. 실제 길이가 목표를 넘어도 영상을 자르지 않는다.
- 제안: 생성 전에는 예상 길이를, 생성 후에는 실제 길이를 보인다.

## 3. 포맷 카드 (format card)

결정: MVP 카드는 3장이다. 이름은 아래와 같다. 이름은 언어 파일 값이다.

| 카드 | 이야기 틀 | 흐름 |
|---|---|---|
| 딱 3가지만 (Just 3 Things) | 목차 1·2·3 (numbered_three) | 「세 가지만」으로 시작, 1·2·3 설명, 한 줄 요약 |
| ○○로 치면 (It's Like…) | 비유 하나 (single_analogy) | 익숙한 대상 하나를 보이고, 개념과 대응을 하나씩, 실제 개념으로 복귀 |
| 만약 ~라면? (What If?) | 가정 (hypothetical) | 「만약」 질문, 결과가 단계마다 커짐, 현실로 복귀 |

- 결정: 카드는 이야기 틀, 화면 틀, 캐릭터 역할, 말투 네 항목을 채운다.
- 제안: 카드 아래에 주제를 넣은 예시 한 줄을 보인다.
- 결정: 카드는 진행 표시, 자막 표시 모드, BGM 분위기, 장면 수도 추천한다. 이 값은 추천값이다. 사용자가 고친 값은 카드를 바꿔도 덮어쓰지 않는다. 덮어써야 하면 먼저 묻는다.

결정: 카드 기본값과 추천값은 아래 표대로다. 값은 바이럴 영상을 관찰해 정했고 시청자 반응으로 검증하지 않았다.

| 항목 | 딱 3가지만 | ○○로 치면 | 만약 ~라면? |
|---|---|---|---|
| 화면 틀 | fixed_stage(고정 무대) | full_stage(장면 중심) | full_stage |
| 캐릭터 역할 | presenter(진행자) | subject(장면 속 인물) | subject |
| 말투 | friendly, 유머 none | friendly, 유머 light | friendly, 유머 light |
| 진행 표시 (추천) | 번호 1·2·3 | 비유 → 연결 → 실제 | 가정 → 결과 1·2·3 → 현실 |
| 자막 방식 (추천) | 문장형 (sentence) | 구절형 (phrase) | 구절형 (phrase) |
| BGM 분위기 (추천) | curious | playful | tense |
| 장면 수 (추천) | 30초 5, 1분 8, 2분 11 | 같음 | 같음 |

## 4. 세부 조정 (fine-tune)

- 결정: 영상의 모든 요소는 사용자가 바꿀 수 있다. 모든 값에 기본값이 있어서 아무것도 고르지 않아도 영상이 나온다. 단, 사용자에게 너무 많은 부하가 들어가면 안 된다.
- 결정: 세 층으로 나눈다.
  - 바로 보이는 것(영상에서 가장 중요한 것): 포맷 카드, 그림체, 테마, 캐릭터, 목소리, 대본, 장면 글.
  - 장면 카드를 열면 보이는 것: 배경, 캐릭터 표정과 위치, 강조 단어, 효과음.
  - 「세부 설정」을 열면 보이는 것: 장면 수, 이야기 틀·화면 틀·캐릭터 역할·말투·유머, 자막 방식과 글꼴, 자막 위치, BGM 크기, 장면 전환, 캐릭터 동작.
- 제안: 화면이 깨질 수 있는 값(자막 위치, BGM 크기, 장면 전환, 동작)은 숫자 입력 대신 검수한 선택지 3~5개로 준다(예: 자막 위치 위·가운데·아래).
- 제안: 기본값과 다르게 바꾼 값에는 표시가 붙고, 항목마다 「기본값으로」 버튼이 있다.
- 제안: 장면 수는 카드 추천값(30초 5, 1분 8, 2분 11)이 기본값이고, 대본 생성 전 세부 설정에서 바꿀 수 있다.

- 결정: 카드를 고른 뒤 「세부 조정」에서 이야기 틀, 화면 틀, 캐릭터 역할, 말투를 하나씩 바꿀 수 있다. MVP에 포함한다.
- 제안: 한 화면에서 고르는 선택지는 3~5개다. 모든 값에 기본값이 있다.
- 제안: 항목별 MVP 값.
  - 이야기 틀: numbered_three, single_analogy, hypothetical (카드 3장과 같다)
  - 화면 틀: fixed_stage(고정 무대), full_stage(장면 중심), dialog_stage(대화창 무대)
  - 캐릭터 역할: none(없음), presenter(진행자), subject(장면 속 인물). 여럿이 대화하는 역할은 MVP 이후다.
  - 말투(register): friendly(한국어 해요체, 영어 friendly conversational), neutral(한국어 설명체, 영어 plain explanatory), casual(한국어 반말, 영어 informal conversational).
  - 유머(humor): none, light. 말투와 따로 고른다.
  - 자막 표시 모드(caption_mode): sentence(문장), phrase(말에 맞춘 구절), typewriter(대화창 타자). typewriter는 dialog_stage에서만 쓴다.
- 제안: 맞지 않는 조합은 막는다. 예: 캐릭터 역할 none에 캐릭터 배치, typewriter와 dialog_stage가 아닌 화면 틀, 현재 그림체에 없는 에셋. 어울림이 약한 조합은 경고만 한다.

## 5. 고정과 변화 (lock)

결정: 사용자가 항목마다 고정과 변화를 고를 수 있다. 목적은 영상끼리 너무 비슷하지 않게 하면서 품질을 유지하는 것이다.

- 결정: 고정한 항목은 프로젝트 안의 모든 영상에서 같다.
- 결정: 변화로 둔 항목은 영상마다 바뀐다.
- 제안: 변화 항목은 LLM이 최근 영상에서 쓴 값을 피해서 고른다.
- 제안: 기본 고정은 그림체, 캐릭터, 목소리다. 기본 변화는 배경, 대화창 모양, 색감, BGM이다.
- 제안: LLM은 검수한 에셋 목록 안에서 에셋 ID만 고른다. 목록에 없는 ID는 렌더러가 거절한다.

## 6. 그림체, 테마, 캐릭터

- 결정: 그림체(art style)는 계속 늘어나는 기본 스타일 묶음이다. 첫 기본 스타일은 픽셀(pixel)이다. 2D 컷아웃(Kenney Modular Characters, CC0)은 첫 개발 빌드 뒤에 넣는다. 요청문이나 참고 영상으로 새 스타일을 만들고 저장해 다시 쓴다.
- 결정: 새 스타일의 합격 기준. 같은 대본에서 머리, 몸, 소품, 배경의 모양이 눈에 띄게 달라야 한다. 「눈을 가늘게」 같은 수정이 실제 그림 모양을 바꿔야 한다. 저장한 스타일은 다음 영상에서 새로 만들지 않고 그대로 불러온다. 색과 글꼴만 바뀐 것은 새 스타일로 치지 않는다.
- 결정: 그림체 안에 테마(theme) 축을 둔다. 테마는 배경, 대화창·자막 상자 모양(skin), 색 팔레트(palette)다.
- 제안: 배경은 장면마다 고른다.
- 결정: 캐릭터는 부위 에셋을 조합해 만든다. LLM이 프리셋 캐릭터를 고쳐 쓸 수 있다.
- 제안: 부위 칸 이름은 그림체끼리 같다: body, face, hair, hat, outfit, prop. LLM은 칸마다 에셋 ID만 고른다.
- 제안: 그림체를 바꾸면 같은 에셋 ID를 새 그림체에서 찾는다. 두 그림체에 모두 있는 에셋 ID만 그대로 유지된다. 없는 에셋은 숨기지 않고 대체안을 보인다.
- 제안: 그림체마다 MVP 수량은 테마 3개(테마마다 배경 3~4장), 부위당 에셋 2~3개다.
- 제안: 동작은 정면 또는 반신 고정 포즈, 표정 바꾸기, 등장 팝, 이동, 페이드까지다. 걷기와 입 모양 맞추기는 MVP 이후다.
- 확인 필요: Kenney 팩의 부위가 6칸에 맞는지 아직 모른다. 모자와 소품은 직접 만들 수 있다. 구현 초기에 확인한다.

## 7. 소리와 자막

- 결정: BGM은 기본으로 켠다. 영상마다 분위기에 맞춰 다르게 고른다. 생성형 음악 모델은 쓰지 않는다.
- 결정: 사용자가 올린 BGM을 쓸 수 있다. BGM을 코드로 만드는 기능도 넣는다. 코드로 만든 음악은 그림을 코드로 그리는 것과 같은 원칙이며 생성형 음악 모델이 아니다. LLM이 쓴 음악 코드는 그리기 코드와 같은 실행기(Pyodide on Deno, 권한 회수)에서 돌리고 WAV만 받는다. 코드 BGM은 첫 개발 빌드에 포함한다. 기술 구현 범위는 짧은 반복 loop WAV의 생성, 저장, 미리 듣기, 재사용이다. PNG와 별도 WAV 검증기를 둔다. 상세 수락은 9a를 따른다.
- 결정: TTS는 자연스러움을 기준으로 고른다.
- 결정: 목소리는 프로젝트 안에서 같게 두는 것이 기본이다. 사용자가 바꿀 수 있다.
- 결정: Qwen3-TTS 0.6B, Qwen3-TTS 1.7B, MOSS-TTS-Nano 100M ONNX, Chatterbox Multilingual V3 ONNX를 시험한다. 같은 한국어 대본의 음성 파일, RTF, cold start, peak RAM을 낸다. 사용자가 듣고 고른다. 제품에는 선택한 엔진 하나만 넣는다.
- 기술 시험안: Qwen 비교 checkpoint는 `Qwen/Qwen3-TTS-12Hz-0.6B-CustomVoice`와 `Qwen/Qwen3-TTS-12Hz-1.7B-CustomVoice`로 시작한다. 이는 사용자 모델 선택이 아니라 비교 재현용 입력이다. 각 후보는 별도 환경에서 실행한다. 실제 full revision, 설정, OS, CPU, RAM, thread 수를 결과에 기록한다. Base checkpoint로 바꿔 클로닝을 시험하면 별도 실험으로 표시한다. 네 후보 비교 승인을 클로닝 UI 승인으로 확대하지 않는다.
- 기술 수락: cold start는 process 시작부터 합성 준비까지 잰다. RTF는 합성 wall time을 실제 WAV 길이로 나눈다. peak RAM은 자식 process를 포함한다. 설치 실패와 청취 부적합도 결과로 남긴다. 전부 실패하면 무음이나 다른 엔진으로 대체하지 않고 TTS 미확정 blocker로 보고한다.
- 기술 설계: 전사와 알려진 대본의 forced alignment는 별도 adapter다. WhisperX는 정렬 기준선이다. 더 가벼운 경로는 한영 정렬 시험을 통과할 때만 대체한다. 화면 글(display_text)과 말할 글(speech_text)의 대응을 기록한다.
- 제안: 맞추기가 실패하면 그 문장은 문장형 자막으로 바꾼다. 실패에는 실행 실패, 일부 단어 누락, 낮은 신뢰도가 모두 포함된다. 글자 수로 나눈 가짜 시간은 만들지 않는다.
- 제안: BGM은 6가지 분위기(curious, playful, tense, energetic, calm, reflective) × 2곡이다. CC0 곡(OpenGameArt)을 먼저 쓴다. 모자라면 Kevin MacLeod 곡(CC BY 4.0)을 쓴다.
- 제안: 곡마다 출처, 라이선스 원문, 권리 증거를 기록한다. CC BY 곡은 앱과 각 출력 영상에 출처와 라이선스를 표시한다. 조건은 [ADR 0010](decisions/0010-source-bgm-with-redistribution-rights.md)을 따른다.
- 제안: Pixabay, Uppbeat, Mixkit, YouTube Audio Library 곡은 기본 목록에 넣지 않는다. 앱에 넣어 배포하는 권한이 없거나 불명확하기 때문이다.
- 제안: 효과음은 Kenney(CC0) 중심으로 7종 16개다: whoosh, pop, ding, click, typing, impact, riser. 장면마다 큰 전환 1개와 핵심 강조 1개 이내로 시작한다.
- 결정: 자막은 핵심어를 강조한다.
- 제안: 자막은 세로 화면 안전 영역 안에 둔다. 1080×1920 기준 자막 상자는 y 1030~1230이다. 한 줄은 한국어 최대 14자, 영어 최대 28자, 최대 2줄이다.
- 제안: BGM은 첫 장면부터 끝까지 끊기지 않고 이어 재생한다. 반복 경계에서 튀는 소리가 없어야 한다.
- 제안: 오디오 시작값은 전체 -16 LUFS, true peak -1 dBTP다. BGM은 말할 때 줄인다(ducking). 휴대폰 스피커로 말이 잘 들리는지 확인한다.

## 8. 장면 수정, 순서, 프리셋

- 결정: 장면 하나 다시 만들기를 MVP에 넣는다. 그 장면만 LLM이 다시 쓴다. 바뀐 장면만 TTS와 렌더를 다시 한다.
- 결정: 장면 카드를 드래그해 순서를 바꾼다.
- 제안: 순서만 바꾸면 장면을 다시 렌더하지 않고 조립만 다시 한다.
- 결정: 프리셋을 저장한다. 프리셋은 저장된 포맷이다.
- 제안: 프리셋에는 포맷 값, 그림체, 테마, 캐릭터 조합, 목소리, 자막과 소리 설정, 고정·변화 설정을 넣는다. 주제, 대본, 장면, 생성 결과는 넣지 않는다.
- 제안: 화면 글만 바꾸면 TTS를 다시 하지 않는다. 말할 글을 바꾸면 그 문장만 다시 합성한다. BGM만 바꾸면 장면 렌더를 다시 쓰고, 소리 섞기와 조립만 다시 한다.

## 8a. 대화 (chat)

- 결정: 입력창은 부가 기능이 아니라 핵심 기능이다. 사용자가 세 가지를 바로 느껴야 한다. 직접 고를 수도 있고 말로 만들 수도 있다. 한 번 만든 것을 쉽게 고친다. 반복해서 만든다. 흐름이 기계적으로 단계를 채우는 느낌을 주지 않게 한다. 확정 배치는 10a를 따른다.

- 결정: 사용자는 대화로도 영상을 고칠 수 있다. 카드와 선택지로 나타내기 어려운 취향을 받기 위해서다.
- 결정: 대화는 모든 단계에 둔다. 입력창은 카드와 같은 패널에 하나만 두고 따로 대화창을 두지 않는다(10a 결정).
- 제안: 단계별 대화의 예. 스토리: 「이 주제로 뭐가 좋을까?」(카드 추천), 「비유는 요리로 해 줘」. 시각: 「좀 더 차분한 색으로」. 소리: 「BGM 덜 신나게」.
- 기술 설계: 대화와 카드와 선택지는 같은 typed 설정을 고친다. 대화 이력 자체를 별도 제작 상태 원본으로 두지 않는다. 새 스타일과 새 템플릿 요청은 6절과 9절의 생성 경로로 연결한다.
- 결정: 카드와 입력 중 하나를 먼저 고르게 하지 않는다. 입력창은 카드 뒤 「추가 지시」가 아니라 생성의 시작점이다. 카드를 고르면 같은 입력창에 카드 표시가 붙고, 문장만 보내면 앱이 포맷을 채운다. 배치는 10a.
- 제안: 카드, 세부 조정, 대화는 같은 값 하나를 고친다. 대화로 바꾼 값은 카드와 선택지 화면에 바로 보인다. 선택지에 없는 취향(「비유: 게임」, 「농담 없음」)은 「추가 지시」 항목으로 화면에 남긴다.
- 제안: 대상을 먼저 고르고 짧게 요청한다. 장면 카드나 항목을 고르면 대화창 위에 「대상: 장면 3」이 붙고 지울 수 있다.
- 제안: 빈 입력창 대신 지금 대상에 맞는 제안 버튼(chip)을 보인다. 예: 장면을 고르면 「짧게」, 「예시 바꾸기」, 「농담 빼기」. 목록은 미리 정해 둔다.
- 결정: 단일 값 하나만 바뀌는 변경(예: 「농담 빼기」가 유머만 바꿈)은 바로 적용하고 「되돌리기」를 준다. 대본을 다시 쓰거나, 여러 장면을 바꾸거나, 고정한 항목을 바꾸거나, TTS나 렌더를 다시 해야 하는 변경은 적용 전에 바뀌는 점과 다시 만들 범위를 보이고 확인받는다. 이 규칙이 10절 기준 26과 10a 되돌리기보다 우선한다.
- 제안: 처리할 수 없는 요청은 적용했다고 답하지 않는다. 할 수 있는 부분과 못 하는 부분을 나눠 말한다.
- 결정: 입력창은 어느 단계에서나 모든 단계의 값을 받는다. 예: 스토리 단계에서 「게임 비유로, 차분한 픽셀에 낮은 목소리로」라고 하면 이야기, 시각, 소리 값이 함께 바뀌고 칩에 보인다. 값만 바꾸고, 음성이나 장면 이미지는 사용자가 다음 행동 버튼을 누를 때 만든다.
- 결정: 한 문장으로 모든 단계의 초안을 채운다. 사용자가 들르지 않은 단계는 기본값과 추천값으로 채운다. 대본 확인 전에는 장면 미리보기를 만들지 않는다는 2절 규칙은 그대로다.
- 결정: 결과 화면에서 바로 고친다. 완성 영상의 장면 썸네일을 누르면 입력창 위에 「장면 3 ×」가 붙고, 「더 짧게」라고 쓰면 장면 3만 다시 만든다. 다섯 단계를 다시 거치지 않는다. 대상은 장면 번호가 아니라 바뀌지 않는 scene ID로 저장한다.
- 제안: 장면 대화의 예: 「3번 장면 더 짧게」, 「여기 농담 하나 넣어 줘」, 「예시를 게임으로 바꿔 줘」. 요청이 한 장면에 해당하면 그 장면만 다시 만든다.
- 제안: 대화로 바꾼 값도 사용자 직접 입력으로 본다. 고정한 항목을 대화가 바꾸려 하면 먼저 묻는다.
- 제안: 대화에서 나온 취향은 사용자가 「프리셋 저장」을 누를 때만 저장한다. 응답마다 저장할지 묻지 않는다.

## 8b. 참고 영상 자동 분석 (reference analysis)

- 결정: 참고 영상 자동 분석을 MVP에 넣는다.
- 결정: 입력은 영상 파일과 링크(YouTube, Instagram, TikTok)다. 링크는 내려받아 분석한다. 플랫폼 이용약관은 링크 기능을 구현할 때 다시 확인한다.
- 결정: 파일 업로드가 기본 경로다. 링크는 내 컴퓨터에서 실행할 때만 위험 안내를 보인 뒤 받는다. 로그인, 쿠키, 보호 조치 우회가 필요한 링크는 실패로 돌리고 파일 업로드를 권한다. 서버 호스팅에서는 링크 다운로드를 끈다.
- 결정: 외부 LLM에는 재료 글, 대본, 참고 영상에서 뽑은 프레임과 받아쓴 대사만 보낸다. 프로젝트 데이터는 내 컴퓨터에만 둔다. 참고 영상 원본과 임시 파일은 분석 뒤 지운다. 첫 실행 때 이 내용을 한 줄로 안내한다.
- 기술 설계: 화면은 ffmpeg로 프레임을 뽑아 LLM에 보인다. 소리는 별도 전사 adapter로 받아쓴다. WhisperX의 정렬 경로와 전사 구현 선택은 분리한다. 무음 비율, BGM 유무, 길이, 장면 수를 측정한다.
- 제안: 분석 결과는 포맷 값을 채운다: 이야기 틀, 화면 틀, 캐릭터 역할, 말투, 자막 방식, BGM 분위기, 색 팔레트, 장면 수. 채운 값에는 「참고 영상」 출처를 표시한다. 사용자는 바꿀 수 있다(추천 순서상 사용자 직접 입력이 먼저다).
- 제안: 카드 3장에 맞지 않는 영상이면 가장 가까운 카드와 다른 점을 보인다. 이때 새 템플릿 코드 쓰기(9절)로 이어 갈 수 있다.
- 기술 설계: 원본 삭제와 복구는 확정 분석값과 검증된 artifact를 기준으로 연결한다. 공급자별 보관 정책 확인과 허용 링크의 실제 성공 여부는 구현 검증으로 남긴다. 링크 경계는 8b의 결정대로 유지한다.

## 9. 데이터와 렌더링

- 결정: 모듈끼리 장면 데이터(scene data) JSON 하나로 주고받는다. LLM은 장면 데이터와 대본만 정한다. 그림은 템플릿 코드가 그린다.
- 결정: 템플릿에 없는 포맷은 상위 모델이 템플릿 코드를 새로 쓰고 프리셋으로 저장한다. 필수 기능에 넣는다.
- 제안: 모델이 쓴 템플릿 코드는 바로 쓰지 않는다. 정해진 템플릿 규칙(입력은 장면 데이터, 출력은 프레임)을 지키는지 검사하고, 시험 장면 하나를 렌더해 통과한 코드만 프리셋으로 저장한다.
- 제안: 렌더링은 Python Pillow와 ffmpeg를 유지한다. 2D 컷아웃 에셋이 SVG면 CairoSVG로 미리 PNG로 바꿔 쓴다. CairoSVG는 LGPLv3이므로 배포 방식을 확인한다.
- 제안: 장면마다 mp4를 만들고 마지막에 이어 붙인다. 장면 전환은 컷과 장면 안 페이드로 시작한다.
- 제안: 정지 미리보기는 렌더링과 같은 함수로 PNG를 만들어 브라우저에 보인다.
- 기술 설계: 실행 계약의 원본과 fixture는 9a를 따른다. 조사 단계의 예시 JSON은 구현 규격이 아니다. 화면 글(display_text)과 말할 글(speech_text)을 나눈다. 단계별 hash로 변경 범위를 계산한다.
- 결정: 모델 라우팅(model routing)을 설계에 넣는다. 흥미와 스토리텔링이 중요한 대본은 상위 모델을 쓴다.
- 제안: 라우팅 표는 설정 파일 한 곳에 둔다. 「딱 3가지만」 대본, 장면 나누기, 장면 데이터는 Haiku 5.5를 쓴다. 「○○로 치면」과 「만약 ~라면?」 대본, 새 템플릿 코드는 상위 모델을 쓴다.
- 결정: 상위 모델은 Claude Sonnet 5.5다.
- 제안: [Anthropic effort 문서](https://platform.claude.com/docs/en/build-with-claude/effort)의 권고를 출발값으로 쓴다. 사용자가 기다리는 대본 쓰기는 Sonnet 5.5 `medium`, 새 템플릿 코드는 `high`, Haiku 5.5의 장면 나누기와 장면 데이터는 `low`, 참고 영상 프레임 보기는 `medium`이다. 문서는 단계마다 자체 평가로 effort를 다시 재라고 하므로, 고정 주제 몇 개로 비교해 바꾼다. effort도 라우팅 표에 둔다.
- 결정: 출력 영상에 앱 이름이나 워터마크를 넣지 않는다.

## 9a. 실행 계약과 프로젝트 연속성

아래는 기술 설계다. 제품 결정을 추가하지 않는다. 계약 구현이 실행 가능한 원본과 fixture를 먼저 만든다. 조사 단계의 예시 JSON은 실행 계약이 아니다.

- Pydantic 원본에 stable scene ID, line ID, schema_version, base revision, style/template digest, origins, lock, artifact 참조를 둔다.
- 한영 정상 fixture는 실제 에셋 ID를 참조한다.
- 잘못된 ID, 중복 순서, 오래된 revision fixture를 함께 둔다.
- 계약 구현은 프로젝트 생성·조회, 대본 생성·확인, 변경 제안·적용·undo, 장면 확인·preview, job 시작·조회·취소·재시도, catalog, 참고 업로드·링크, artifact 다운로드, 다음 영상 생성의 OpenAPI를 만든다.
- API마다 method, path, 입출력, 오류, 중복 요청 처리, revision 충돌 응답을 고정한다.
- TS 타입은 이 OpenAPI에서 생성한다.
- job 상태는 queued, running, succeeded, failed, cancelling, cancelled다.
- job 행은 실행 전에 삭제하지 않는다.
- 상태 점유는 원자적으로 전환한다.
- checkpoint는 성공 artifact 검증 뒤 기록한다.
- 취소는 자식 process 전체를 종료한다.
- 취소 뒤 도착한 결과와 오래된 revision 응답은 채택하지 않는다.
- 재시작은 성공 artifact의 존재와 digest를 재검사한 뒤 재사용한다.
- 외부 LLM의 과금 취소까지 보장하지 않는다.
- adapter별 timeout, 최대 재시도, 전체 job deadline을 설정한다.
- 인증·한도 오류와 재시도 가능한 연결 오류를 구분한다.
- 429 대기 중에도 취소를 받는다.
- 엔진, 목소리, 모델 변경이나 재생성 범위 확대는 조용히 수행하지 않는다.
- 무거운 모델 worker는 한 번에 하나로 시작한다.
- typed 프로젝트 설정과 영상별 immutable snapshot을 원본으로 둔다.
- 대화와 요약은 확정값과 lock을 덮지 못한다.
- 현재 영상 수정은 프로젝트 기본값을 자동 갱신하지 않는다.
- 프리셋 저장은 사용자 명시 동작으로만 한다.
- 다음 영상은 이전 설정을 복사하고 주제와 대본을 비운다.
- 과거 영상 snapshot은 다음 영상 수정으로 바뀌지 않는다.
- 재시작과 긴 대화 뒤에도 직접값, lock, 과거 영상 불변을 시험한다.
- Windows DATA_DIR 기본은 사용자 LocalAppData 아래 앱 전용 폴더다.
- Linux DATA_DIR 기본은 XDG_DATA_HOME 아래 앱 전용 폴더다.
- Linux CACHE_DIR 기본은 XDG_CACHE_HOME 아래 앱 전용 폴더다.
- XDG 환경변수가 없으면 각각 `~/.local/share/`와 `~/.cache/` 아래를 쓴다.
- Windows CACHE_DIR는 사용자 LocalAppData 아래 별도 cache 폴더다.
- MODEL_DIR 기본은 DATA_DIR 아래 models 폴더다.
- 계약 구현은 앱 ID를 정한 뒤 설정에서 정확한 경로를 생성한다.
- 프로젝트 삭제는 해당 프로젝트 데이터만 지운다.
- cache 청소는 revision, undo, 저장 스타일이 참조하는 artifact를 지우지 않는다.
- uninstall은 사용자 프로젝트와 모델을 기본 보존한다.
- 정지 미리보기는 대본 확인 뒤 구도 검수용으로 만든다.
- TTS 전 길이는 예상값으로 표시한다.
- 확정 음성 뒤에는 preview와 mp4가 같은 timing artifact를 읽는다.
- 글, font, style, revision이 바뀌면 오래된 preview를 완료 상태로 표시하지 않는다.
- 단계별 cache key는 `services/pipeline/cache_keys.py` 한 곳에서 계산한다.
- 화면 글 변경은 TTS를 무효화하지 않는다.
- 순서 변경은 조립만 무효화한다.
- BGM 변경은 mix와 조립만 무효화한다.
- 완성·검증 뒤 atomic rename한 artifact만 성공 index에 연결한다.
- 코드 BGM의 최소판은 짧은 loop 하나를 생성·저장·미리 듣기·재사용한다.
- 기술 시작값은 mono PCM16, 44.1 kHz, 최대 16초다.
- 이 값은 제품 결정이 아니라 runtime probe로 검증할 자원 상한이다.
- 코드 BGM은 승인된 sandbox에서 허용 stdlib 합성 API만 쓴다.
- 외부 sample, package 다운로드, host 파일 접근은 금지한다.
- 부모의 별도 WAV 검증기가 RIFF 구조, 실제 frame 수, sample rate, channel, 출력 bytes를 검사한다.
- host sound 서비스가 loop 반복과 영상 길이를 처리한다.
- code/runtime digest, seed, 설정이 같으면 WAV를 재사용한다.
- 실패하면 이전 BGM을 보존한다.
- 고정 코드 WAV, 잘못된 header, 초과 길이, stdout flood, 무한 계산, cache hit를 시험한다.
- BGM 교체 시 장면 renderer 호출은 0이어야 한다.
- 사용자 BGM 업로드는 job 전용 ID로 저장한다.
- 고정 decoder로 제한한 내부 오디오로 변환한다.
- 손상 파일과 초과 bytes·길이는 거절한다.
- 업로드 BGM 보존은 참고 영상의 분석 후 원본 삭제 정책과 구분한다.
- 업로드 BGM은 프로젝트가 참조하는 동안 보존한다.
- 한영 font 파일과 digest와 원본 라이선스를 동봉한다.
- 실제 glyph와 픽셀 폭으로 줄바꿈한다.
- 긴 한글, 영문 식별자, 숫자, 괄호, 혼합문자, 누락 glyph, 자모 분리, 타자 효과 fixture를 시험한다.
- OS 기본 font로 조용히 대체하지 않는다.
- job, attempt, stage, 실제 provider/model, effort, cache hit, usage, 재생성 scene ID, monotonic 시작·끝을 기록한다.
- 전체 wall time과 병렬 단계 시간은 구분한다.
- 사용자 조작 시간은 초안 편집 시작부터 다음 행동까지의 활성 구간을 잰다.
- 대기와 비활성 탭 시간은 조작 시간에서 분리한다.
- provider 사용량을 API 현금 비용으로 환산하지 않는다.
- 미확인 비용은 0이 아니라 null이다.
- 기본 로그는 ID, 오류 코드, 시간, 실제 모델, usage만 남긴다.
- prompt, 대사, 참고 URL, 키, 원본 프레임은 기본 수집하지 않는다.
- offline은 기존 프로젝트 열기·편집·결과 재생의 가능 범위를 표시한다.
- 로컬 모델이 준비됐으면 가능한 음성·렌더 경로를 구분한다.
- LLM이 필요한 생성·참고 분석은 연결 필요를 알린다.
- 누락 모델은 정확한 항목을 알린다.
- 전체 offline 앱이라고 설명하지 않는다.

## 10. 완료 기준

결정: 완료 기준은 1~30의 번호를 유지한다. 기준 6·7·17은 6절의 새 스타일 합격선을 따른다. 기준 28은 발음 수정 제외 결정을 따른다.

1. 한 문장 입력 → 초안 → 대본 확인 → 장면 확인 → 실제 생성 → mp4가 한국어와 영어에서 각각 동작한다. 선택 화면은 방문하지 않아도 된다. 대본 확인과 장면 확인은 생략하지 않는다.
2. 대본을 확인하기 전에는 장면 미리보기가 만들어지지 않는다.
3. 같은 주제로 카드 3장을 고르면 이야기 흐름이 서로 다른 대본이 나온다.
4. 세부 조정에서 이야기 틀, 화면 틀, 캐릭터 역할, 말투를 바꾸면 결과에 반영된다. 맞지 않는 조합은 막힌다.
5. 카드를 바꿔도 사용자가 직접 고친 값은 그대로 남는다.
6. 고정 그림체 두 개만으로는 통과하지 못한다. 첫 기본은 픽셀이다. 기본 그림체마다 테마 3개를 둔다. 테마 변경은 배경, 상자 모양, 색 팔레트에 반영된다. 새 스타일은 6절에 따라 같은 대본의 머리, 몸, 소품, 배경 형태가 눈에 띄게 달라야 한다. 색과 글꼴만 바뀌면 실패다. 컷아웃은 첫 개발 빌드의 필수가 아니며 뒤에 넣는다.
7. 새 스타일 결정에 따라 「눈을 가늘게」 요청 전후의 실제 형태 차이를 확인한다. 스타일을 바꿀 때 공통 부위 ID는 유지한다. 없는 에셋은 대체안을 표시한다. 두 기본 그림체 사이의 호환 시험은 컷아웃이 들어간 뒤 수행한다.
8. 고정·변화가 동작한다. 같은 프로젝트에서 두 번 만들면 고정 항목은 같다. 후보가 둘 이상인 변화 항목은 달라진다. 두 영상 모두 검수 목록의 에셋 ID만 쓰고 조합 규칙을 지킨다.
9. 프로젝트 안의 두 영상이 같은 목소리를 쓴다. 사용자가 목소리를 바꾸면 그 뒤 영상에 반영된다.
10. 장면 하나 다시 만들기에서 다른 장면의 렌더 파일은 다시 만들어지지 않는다.
11. 화면 글만 고치면 TTS 캐시를 다시 쓴다. 말할 글을 고치면 그 문장만 다시 합성한다.
12. 드래그로 순서를 바꾸면 장면 렌더 없이 새 순서의 mp4가 나온다.
13. 프리셋을 저장하고, 새 영상에 불러와 같은 포맷으로 만든다.
14. BGM이 처음부터 끝까지 끊기지 않는다. 반복 경계 튐과 클리핑이 없다. 핵심어 강조 자막이 나온다.
15. 화면 글과 말할 글이 다른 문장(숫자, 영어 코드명)에서 자막 시간이 맞는다. 맞추기가 실패한 문장은 문장형 자막으로 나온다.
16. 화면 글자가 한국어와 영어 언어 파일로 바뀐다.
17. 카드 3장에 없는 포맷을 요청하면 상위 모델이 템플릿 코드를 쓴다. 검사와 sandbox 시험 렌더를 통과한 코드만 저장한다. 새 스타일 결정에 따라 저장한 스타일과 템플릿은 다음 영상에서 스타일 생성 호출 없이 재사용한다. 6절의 형태 생성과 수정 시험을 함께 통과해야 한다.
18. 재료로 붙여넣은 글의 내용이 대본에 반영된다.
19. 장면 단계나 결과 화면에서 장면 3을 고르고 「더 짧게」를 요청하면 3번 장면만 바뀌고 다시 만들어진다. 다섯 단계를 다시 거치지 않는다. 대화로 고친 값은 카드를 바꿔도 남는다.
20. 참고 영상 파일이나 링크를 넣으면 포맷 값 일부가 「참고 영상」 출처로 채워진다. 사용자가 그 값을 바꿀 수 있다.
21. 새 Windows와 Linux 환경에서 받은 설치 파일로 실제 영상을 만든다. Python과 CPU wheel과 검증한 binary는 동봉한다. 모델은 manifest와 SHA-256으로 첫 실행에 준비한다. 배포판의 사용자 인증은 API 키다. 개발판은 설정된 OpenAI-compatible endpoint를 기본으로 호출한다. key가 필요하면 keyring 또는 env에서 읽는다. 공식 CLI는 개발용 선택지다. 두 profile을 따로 시험한다. 설치 수락은 [ADR 0012](decisions/0012-package-for-windows-and-linux.md)를 따른다.
22. 같은 코드가 설정만 바꿔 직접 실행과 서버 호스팅(한 명)에서 모두 동작한다. 서버 호스팅은 직접 실행 뒤에 확인한다.
23. 모바일 폭(390px)과 데스크톱 폭(1440px)에서 다섯 단계를 모두 끝낼 수 있다.
24. 그림체마다 자막 글꼴 2~3개 중에서 고를 수 있다.
25. 「이 영상으로 새 영상 만들기」를 누르면 포맷, 그림체, 캐릭터, 목소리가 그대로 들어오고 주제와 대본은 비어 있다.

아래 26~30은 제작자와 시청자 니즈 조사에서 나온 기준이다.

26. 대화로 3번 장면을 고치면 적용 전에 글, 화면, 다시 만들 범위를 비교해 보인다. 적용 뒤 바뀌지 않은 장면 파일의 해시는 같다. 앞뒤 장면에 남은 옛 표현(예: 비유를 요리에서 게임으로 바꿨는데 2번에 남은 요리 표현)은 경고만 하고 자동으로 고치지 않는다. 되돌리기를 누르면 이전 대본과 결과가 돌아온다.
27. 초안부터 mp4까지 사용자 조작 시간, 기다린 시간, LLM 사용량, 다시 만든 범위를 기록한다. 비용을 모르면 「미확인」으로 보인다. 앱 강제 종료, LLM 한도, TTS 실패, 조립 실패 뒤에도 성공한 결과와 마지막 저장 상태를 다시 쓴다.
28. 한국어와 영어 검수 대본(숫자, 약어, 고유명사, 질문, 농담 포함)을 휴대폰으로 듣는다. 잘못 읽은 곳, 목소리가 바뀐 곳, 말을 덮는 BGM을 기록한다. 자연스러움 합격선은 이 청취 뒤 정한다. 결정: 발음 수정은 MVP 전체에서 제외한다.
29. 390px 미리보기와 1080×1920 출력에서 긴 단어, 숫자, 코드, 타자 자막이 잘리지 않고 플랫폼 UI에 가리지 않는다. 소리를 끄고 봐도 핵심 정보가 남는다. 미리보기와 mp4의 자막 글과 시간이 같다. 전체 대사 자막(SRT)도 함께 내려받을 수 있다.
30. 생성 직전에 「출력 전 확인」을 보인다: 첫 화면의 약속, 끝에서의 답, 사실 주장과 재료의 대응, 가정 표시. 앱은 사실 검증을 보증하지 않는다. 결정: AI 음성 사용과 플랫폼별 AI 표시 안내는 넣지 않는다.

## 10a. 화면 상태 (UX states)

항목별 「결정」과 「제안」을 구분한다. 표시가 없는 UX 세부는 기술 운영안이다. UI 배치는 결정됐다. 시각 디자인의 글꼴(Pretendard), 대표색(#3182F6), 모양 규칙의 원본은 [ADR 0016](decisions/0016-use-selected-design-tokens.md)이다. 나머지 값은 디자인 작업에서 정한다.

- 첫 실행: 배포판은 API 키를 받는다. 개발 빌드는 설정된 dev endpoint의 연결과 호출을 검사한다. 공식 CLI를 선택한 경우에만 CLI 로그인과 호출을 검사한다. 앱은 모델 준비 진행을 보인다. 인증 실패는 profile에 맞게 안내한다. 준비 뒤 첫 화면은 10a의 큰 입력창과 카드 배치를 따른다.
- 저장과 재개: 프로젝트와 영상은 자동 저장한다. 프로젝트 목록에서 다시 열면 멈춘 단계부터 이어 한다. 피드 화면은 아니고 목록만이다.
- 앞 단계로 돌아가기: 주제, 언어, 카드, 그림체, 목소리를 바꾸면 무엇이 다시 만들어지는지(대본, 미리보기, TTS, 렌더) 실행 전에 보인다.
- 되돌리기: 확인 규칙은 8a를 따른다(값 하나는 바로 적용, 대본·여러 장면·다시 만들기는 적용 전 확인). 적용 뒤에도 바로 전 상태로 한 번 되돌릴 수 있다. 실패하면 이전 결과를 그대로 둔다.
- 기다리기: LLM, TTS, 렌더 중에는 지금 하는 일과 끝난 장면 수를 보인다. 취소할 수 있다. 같은 작업을 두 번 실행하지 않는다. 근거 없는 남은 시간은 보이지 않는다.
- 실패: LLM 오류, 로그인 만료와 사용 한도, TTS, 렌더, 템플릿 검사 실패를 각각 쉬운 말로 알린다. 실패한 부분만 다시 실행한다.
- 대화와 카드: 대화가 어느 장면, 어느 값을 고치는지 보인다. 요청이 모호하면 한 번 묻는다. 대화로 바꾼 값은 카드와 선택지 화면에도 바로 반영된다.
- 사용자가 준 대본: 기본은 그대로 쓰고 장면만 나눈다. 고쳐 쓰려면 먼저 묻는다.
- 고르기 전 미리 보기: 카드, 그림체, 테마, 캐릭터는 대표 이미지로 보인다. 값마다 「추천」, 「고정」, 「변화」 중 어느 상태인지 보인다. 맞지 않는 조합은 이유를 보인다.
- 장면 카드: 화면 글과 말할 글을 따로 고칠 수 있다. 순서를 바꿔 흐름이 깨지면 경고한다. 장면 추가와 삭제는 허용한다.
- 미리 듣기: 목소리와 BGM을 생성 전에 짧게 들어 볼 수 있다.
- 결과: 1080×1920, 30fps mp4를 재생하고 내려받는다. CC BY 곡을 썼으면 출처 문구를 함께 보인다.
- 시간과 비용: 다시 만들기 전에 몇 장면이 다시 만들어지는지 보인다. 끝나면 실제 걸린 시간을 보인다.
- 접근성: 드래그 대신 위아래 버튼으로도 순서를 바꾼다. 강조는 색만 쓰지 않는다. 필수 기능의 keyboard 이동과 focus 복귀를 시험한다. chip 삭제, 장면 선택, 모달, 오류, 진행 상태에 접근 가능한 이름을 준다. reduced motion을 확인한다. 전면 WCAG 인증이라고 보고하지 않는다.
- 기기: 모바일과 데스크톱 모두 지원하는 적응형 UI다(결정). 결정: 두 기기에서 같은 경험을 주되, 화면 배치가 어느 쪽에서도 불편하지 않아야 한다.
- 제안(배치 공통): 모든 단계의 중심은 9:16 미리보기다. 같은 경험은 같은 단계, 같은 값, 같은 되돌리기, 같은 결과를 뜻한다. 모든 패널을 한 화면에 욱여넣는다는 뜻이 아니다.
- 결정: 카드와 입력창을 한 패널에 합친다. 대화창을 따로 두지 않는다.
- 결정(배치): 첫 화면은 두 기기 모두 가운데에 「어떤 영상을 만들까요?」 큰 입력창, 그 아래 언어·길이, 그 아래 「직접 골라도 돼요」와 카드 3장(카드마다 주제 예시 한 줄)이다. 카드를 먼저 골라도 되고 문장만 보내도 된다. 초안이 생긴 뒤에는 입력창이 패널 맨 아래에 고정되고, 바로 위에 지금 값 칩 한 줄(예: 「○○로 치면 | 비유: 편의점 재고 | 픽셀 | 1분」), 그 위에 지금 단계의 카드와 선택지가 온다. 칩을 누르면 그 값의 선택지가 열린다. 다음 행동 버튼(대본 확인, 생성, 다운로드)은 두 기기 모두 오른쪽 위에 둔다. 아래 입력창과 겹치지 않게 하기 위해서다. 단계는 순서대로 거치지 않아도 된다. 데스크톱은 위쪽 단계 탭, 모바일은 「스토리 ▾」 메뉴로 아무 단계나 연다.
- 제안(데스크톱, 디자인 작업에서 확정 전): 위쪽 바에 단계 탭과 다음 행동 버튼. 편집 카드와 9:16 미리보기, 장면 선택의 위치와 폭은 디자인 작업의 시안 비교 뒤 정한다. 대화 기록은 접어 두고 펼쳐 본다. 앱의 답은 말풍선으로 쌓지 않고 칩과 카드 값이 바뀌는 것으로 보인다. 창이 좁아져도 미리보기를 찌그러뜨리지 않는다.
- 결정(모바일): 위쪽 바에 「스토리 ▾」 단계 메뉴와 다음 행동 버튼. 그 아래 작은 9:16 미리보기(스크롤하거나 키보드가 열리면 작은 썸네일로 접힘), 장면 썸네일 가로 줄, 지금 단계 카드·선택지, 값 칩, 맨 아래 고정 입력창. 근거: 대화형 도구의 아래쪽 입력창 관례, Captions 편집 화면의 아래 입력창, 키보드가 아래에서 올라옴. 아래쪽이 엄지에 늘 편하다는 근거는 약하다. 실기기 확인 전이다.
- 제안(모바일 단계별): 스토리는 카드 3장을 세로 목록으로 보인다. 시각은 그림체, 테마, 캐릭터 중 한 분류만 한 번에 보인다. 장면은 대본 확인을 전체 화면으로 하고, 확인 뒤 선택 장면 미리보기와 아래 가로 썸네일 줄을 보인다. 순서 바꾸기는 「순서」 버튼으로 세로 목록을 열고 손잡이로 끌거나 「앞으로 / 뒤로 / 위치로 이동」을 누른다. 소리는 「목소리 / BGM / 자막」 탭이고, 듣기 버튼과 선택 버튼을 나눈다. 생성은 9:16 플레이어가 주 화면이고 「생성」 또는 「다운로드」 버튼 하나만 위쪽 바에 둔다.
- 제안(터치): 주요 터치 영역은 48×48 CSS px를 시작값으로 한다. 끌기는 손잡이에서만 시작하고, 끌지 않는 대안을 항상 둔다(WCAG 2.2 SC 2.5.7). 길게 누르기와 쓸어 넘기기만으로 필수 기능을 숨기지 않는다. 화면 회전과 크기 변경은 선택, 쓰던 글, 되돌리기를 초기화하지 않는다.
- 제안(아래쪽 패널): 짧은 조작(모자 고르기, BGM 크기)에만 쓴다. 패널 위에 패널을 겹치지 않는다. 대본 전체 편집처럼 긴 작업은 전용 화면으로 연다(NN/g 2023).
- 결정: 모바일 브라우저는 같은 와이파이의 컴퓨터 앱에 접속한다. 로컬 모델은 컴퓨터에서 실행한다. 휴대폰 단독 로컬 실행은 지원한다고 적지 않는다. LAN 보안은 CONTRACTS 13.2절을 따른다.

## 11. MVP에서 하지 않는 것

결정: 생성형 이미지·영상·음악 모델, 타임라인 편집, 사진으로 캐릭터 만들기, 프로젝트 피드, 시리즈 화면, 공유, 로그인.

기술 범위: 여럿이 대화하는 캐릭터 역할, 걷기, 입 모양 맞추기는 MVP 이후다. 결정: 발음 수정은 MVP 전체에서 제외한다.

## 12. 검증 계획과 남은 입력

- 결정: 10절 완료 기준 30개를 확정한다. 3절 카드 기본값도 확정한다. SPEC의 나머지 「제안」 표시 항목은 구현 세부이며 필요할 때 확인한다.
- 결정: 모바일은 같은 와이파이에서 휴대폰 브라우저로 내 컴퓨터의 앱에 접속해 시험한다.
- 결정: Windows는 사용자별 설치 exe, Linux는 tarball이다. 저장소는 개인 GitHub의 공개 저장소로 처음부터 운영한다. 코드 라이선스는 Apache-2.0이다.
- 결정: 실제로 써 보고 피드백할 수 있는 개발 빌드를 먼저 만든다. 참고 영상 분석, 새 템플릿 코드, 설치 파일, 난이도가 낮은 기능을 넣고 발음 고치기는 뺀다. 서버 호스팅은 MVP의 중심이 아니며 나중에 배포할 때 다룬다.
- 결정: 기기 없이 하는 모바일 시험은 세 겹이다. ①Playwright 기기 에뮬레이션(iPhone, Pixel 프로필, Chromium과 WebKit)으로 390px 화면 다섯 단계 완주와 스크린샷을 자동 시험한다. 구현 변경마다 돌린다. ②각자 컴퓨터 Chrome DevTools 기기 모드로 직접 눌러 본다. ③Android Studio 에뮬레이터의 Chrome으로 가상 키보드가 아래 입력창을 가리는지 본다. 한계: ①②는 실제 가상 키보드, 실제 손가락 터치, iOS Safari 동작을 재현하지 못한다. Playwright WebKit은 iOS Safari가 아니다. 그래서 실기기 시험은 마지막에 한 번 한다. 같은 와이파이가 안 되면 Tailscale이나 터널로 접속한다.
- 결정: 화면 구성은 장면 카드에서 직접 고른다(배경, 캐릭터 표정과 위치, 강조 단어, 효과음; 4절 세 층). 대본은 직접 넣을 수 있다.
- 결정: 자막 글꼴은 그림체마다 어울리는 글꼴 2~3개 중에서 고른다. 라이선스를 확인한 무료 글꼴만 앱에 넣는다.
- 결정: 「이 영상으로 새 영상 만들기」 버튼을 둔다. 그 영상의 포맷, 그림체, 캐릭터, 목소리를 가져오고 주제와 대본은 비운다. 프리셋과 같은 데이터를 쓴다.
- 결정: 프로젝트 피드, 시리즈 화면, 공유, 로그인은 이번 MVP에서 뺀다. 나중에 구현할 때 인스타그램 등 SNS를 참고한다.
- 결정: 화면은 모바일과 데스크톱에 맞춰 바뀌는 적응형 UI(responsive)로 만든다.
- 결정: 제작자와 시청자 니즈는 조사로 확인한다. 이후 사용자 피드백도 받는다.
- MVP 이후 후보: 파일, 사진, 동영상 재료.
- 열린 결정: 시각 디자인의 나머지 값이다.
- 결정: 리뷰 봇은 모든 PR의 cubic이다. 제한되면 별도 독립 리뷰로 전환한다. 병합 규칙은 [CONTRIBUTING](../CONTRIBUTING.md)을 따른다.
- 열린 결정: 네 TTS 비교 결과를 듣고 제품 엔진을 고른다.
- 기술 구현 대기: 핵심어 범위 표현, 실행 가능한 schema와 OpenAPI, 모듈별 fixture는 계약 구현이 닫는다.
- 기술 검증 대기: 양 OS 설치와 sandbox 거부 시험, 선택 TTS 속도와 청취, BGM 곡별 권리, 한국어 font, 링크 성공 여부다.
- 후속 확인: Kenney 부위 구조와 컷아웃 호환 시험이다.
